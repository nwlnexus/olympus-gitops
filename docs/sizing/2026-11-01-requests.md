# Container requests from measured usage (2026-11-01)

Step 1 of nwlnexus/olympus-sdk#707. Every running non-DaemonSet container outside `kube-system` and
`flux-system` gets CPU and memory requests sized from its measured usage, so the scheduler (and later the
descheduler) sees real load. No limit was added, removed or lowered; one was raised (prometheus-server memory, 2Gi to 3Gi, owner decision; see "Conflicts").

## Method

- Source: the in-cluster Prometheus (`prometheus-server.observability`), cAdvisor series, queried 2026-11-01.
- CPU: `quantile_over_time(0.95, (max by (namespace,pod,container)(rate(container_cpu_usage_seconds_total{container!="",container!="POD"}[5m])))[7d:5m])`,
  and the same with `max_over_time` for the max column.
- Memory: the same over `container_memory_working_set_bytes`.
- Pods are folded into their owning workload (the highest value across the workload's pods is used).
  `max by` instead of `sum by` avoids double counting while a container restarts (old and new cAdvisor series overlap).
- CPU request = max(p95 x 1.2, 10m), rounded up: 10m steps to 50m, 25m steps to 100m, 50m steps to 500m, then 100m.
- Memory request = max(p95 x 1.2, 32Mi), rounded up: 16Mi steps below 128Mi, 32Mi steps below 512Mi, then 64Mi.
  For Go and ML workloads whose 7-day max is more than 1.2 x their p95 (spiky), and for ML/TSDB workloads
  (embedder, prometheus-server), the max working set replaces the p95 ("Mem basis" column).
- Workloads younger than 7 days use the data that exists: `litellm` (Deployment created 4 days earlier) and the
  `olympus-arm64` listener (recreated about 1 day earlier, olympus-sdk#701).

Notes on the table:
- `memory-embedder`: memory follows the rule (7-day max 2052Mi x 1.2 = 2496Mi, under the 3Gi limit). CPU stays at 2:
  the 14m p95 is idle time, and the request is the throughput reservation documented in `embedder.yaml`
  (about 7 embeddings/s per CPU). This is a judgement call; the rule would give 20m.
- `prometheus-server`: the 7-day max working set x 1.2 is 2368Mi and the p95 x 1.2 is 2240Mi, both above the
  old 2Gi limit. Owner decision 2026-11-01: the memory limit is raised from 2Gi to 3Gi (the 7-day peak of 1994Mi
  was 97% of the old limit) and the request is the p95 figure, 2240Mi. See "Conflicts".
- `redpanda` broker: kept. The chart derives the container's requests and limits (both) from
  `resources.cpu.cores` and `resources.memory.container.max` and passes the same values to Redpanda as
  `--smp`/`--memory`, so a request cannot be set independently without changing the limit.
- `whoami` and `blackbox-exporter`: the new memory request equals the existing memory limit (32Mi and 64Mi).
- The tailscale proxies (`ts-*`) are created by the operator, so their requests come from two new ProxyClasses
  (`proxy-sized` as `proxyConfig.defaultProxyClass`, `proxy-sized-otlp` selected by a label on the `otlp-ts` Service).
  Changing a proxy's ProxyClass restarts its pod (a short tailnet blip for that Service).
